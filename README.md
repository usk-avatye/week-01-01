# Campaign Guard: 캠페인 예산 가드

광고주가 캠페인 예산을 정하고 모의 집행을 요청하는 웹 서비스입니다. 예산을 넘는 집행을 거절하고, 응답 유실로 같은 요청을 재전송해도 비용은 한 번만 반영합니다. 실제 광고, 결제 연동은 없습니다.

Node.js **20.20.2**, TypeScript, Express 5, `pg`, PostgreSQL을 사용합니다. 별도 프런트 서버 없이 같은 Express 서버가 웹 화면과 API를 제공합니다.

## 실행

프로젝트 루트에서 실행합니다. 처음 설치할 때 인터넷이 필요합니다. 로컬 PostgreSQL은 개발 의존성에 포함된 실제 네이티브 PostgreSQL 18.4이며, DB 모형이나 메모리 DB가 아닙니다. 기본 포트는 DB `55432`, 웹 `3000`입니다.

```sh
npm ci
cp .env.example .env
npm run db:start
```

위 터미널을 유지한 채 두 번째 터미널에서 실행합니다.

```sh
npm run db:migrate
npm run db:seed
npm run build
npm start
```

[http://localhost:3000](http://localhost:3000)에서 확인합니다. 개발 시 변경 후 `npm run build`를 실행하고 API 코드를 바꿨다면 서버도 재시작합니다. `npm run dev`는 빌드 후 서버 시작이며 파일 감시 명령은 아닙니다.

`.env`가 이미 있다면 덮어쓰지 마세요. `DATABASE_URL`과 `TEST_DATABASE_URL`로 외부 PostgreSQL을 사용할 수 있습니다. 테스트 DB 이름은 `_test`로 끝나야 합니다. 웹 주소를 바꾸면 `APP_ORIGIN`과 실제 접속 주소를 일치시킵니다.

로컬 DB 데이터는 `.local/postgres`에 남습니다. `db:start`, 마이그레이션, 서버 재시작은 데이터를 초기화하지 않습니다. DB와 웹 서버는 각 터미널에서 Ctrl+C로 종료합니다. `.env.example`의 비밀번호는 로컬 시연용이며 공개 운영에 사용하지 않습니다.

## 시연 계정

기본 `DEMO_PASSWORD`는 `Demo-Campaign-2026!`입니다.

| 진입 화면 | 이메일 | 역할 |
| --- | --- | --- |
| 광고주 로그인 | advertiser-a@example.test | 광고주 A |
| 광고주 로그인 | advertiser-b@example.test | 광고주 B |
| 관리자 로그인 | admin@example.test | 관리자 (조회 전용) |

새 계정은 회원가입 화면에서 만들 수 있습니다. 비밀번호는 15~128자입니다. 가입자는 항상 광고주입니다. 관리자 계정은 시드로만 만듭니다. `db:seed`를 반복해도 기존 비밀번호, 예산, 집행 금액, 순번을 덮어쓰지 않습니다. 이전 시연 이름은 짧은 이름으로 정리하고 표시 이름에서 가운데점을 제거합니다. 이미 같은 이메일이 다른 역할이면 승격하지 않고 실패합니다.

## 핵심 동작

- 캠페인은 일시정지 상태로 생성합니다. 시작하거나 정지할 수 있고, 일시정지 중에만 총예산을 수정할 수 있습니다. 이미 사용한 금액보다 낮출 수 없습니다.
- ‘요청 번호 준비’는 캠페인별 DB 순번을 발급합니다. 준비 자체에는 비용이 없습니다.
- 집행 금액은 1~1,000,000,000원 정수입니다. 예산 범위 안이면 전액 승인, 일시정지, 예산 부족이면 비용 없이 거절합니다.
- 같은 캠페인, 번호와 금액의 재전송은 원래 결과와 처리 시각을 돌려줍니다. 같은 번호에서 금액만 바꾸면 409입니다.
- 거절 뒤 예산을 늘리거나 재개해도 원래 거절은 바뀌지 않습니다. 새 판단은 새 번호로 요청합니다.
- 브라우저는 집행 전 번호와 금액을 보관합니다. 응답을 확인하지 못하면 같은 요청을 조회하거나 재전송하는 것만 허용합니다. GET이 ‘준비’여도 늦은 POST가 올 수 있어 번호를 풀지 않습니다.
- 관리자 화면은 모든 광고주의 캠페인, 이력 조회만 제공합니다. 권한은 화면이 아니라 API에서 검사합니다.

## 구조

`app.ts`는 의존성 조립만 합니다. 한 객체가 회원, 예산, 집행, 관리자 기능을 전부 맡지 않습니다.

| 경계 | 책임 |
| --- | --- |
| `src/server/auth` | 회원가입, 비밀번호, DB 세션, 역할, CSRF 검사 |
| `src/server/campaigns` | 소유자 캠페인 조회, 예산, 상태 변경 |
| `src/server/executions/decision.ts` | 상태, 예산에 대한 순수 업무 판단 |
| `src/server/executions/service.ts` | 준비, 집행의 트랜잭션 순서 |
| 기능별 `repository.ts` | 매개변수화 SQL과 DB 행 변환 |
| 기능별 `routes.ts` | HTTP 입력과 응답 연결 |
| `src/server/admin` | 관리자 전용 읽기 쿼리와 라우트 |
| `src/contracts` | 서버와 브라우저 사이 DTO, 식별자는 문자열 |
| `src/client/main.ts` | 경로 선택과 화면 조립 |
| `execution-controller`, `execution-flow`, `pending-store` | 통신 조율, 결과 판별, 요청 정보 보관 |
| 나머지 `src/client` 화면 모듈 | 기능별 DOM 렌더링 |

모든 캠페인 변경은 **캠페인 행 → 집행 행** 순서로 잠급니다. 이미 끝난 요청을 먼저 확인한 뒤 현재 캠페인 조건을 판단합니다. 예산 차감과 결과 저장은 같은 트랜잭션이며 커밋 후 HTTP 응답을 보냅니다. 프로세스 내부 락에 의존하지 않습니다.

## 검증과 발표

DB 실행 상태에서 다음 명령을 사용합니다.

```sh
npm test
npm run build
```

테스트는 전용 DB 안에 임시 스키마를 만들고 해당 스키마만 정리합니다. 예산, 중복 처리, 잠금 순서 검증은 실제 PostgreSQL과 HTTP를 사용합니다. 응답 유실, 지연은 테스트 프록시로 재현하고 롤백은 테스트 DB 트리거로 재현합니다. 운영 API에 장애 주입 스위치는 없습니다.

설계, ERD, API, 구현 계획, 검증 기록과 발표 자료는 로컬 `docs/` 폴더에서 관리합니다. 이 폴더는 Git에서 제외합니다. 업무 용어는 [GLOSSARY.md](GLOSSARY.md)에 정리했습니다.

이번 버전은 로컬 DB 한 대이며 DB 장애 시 중단됩니다. 분산 DB, 고가용성, 대규모 성능 검증은 확장 설계로 남겨 두었습니다. 이메일 인증, 비밀번호 재설정, Google 로그인, 실제 광고 집행, 결제도 이번 범위에 포함하지 않습니다.
